## Background

元素可见或 URL 变化不一定表示 SPA 列表已经刷新。业务脚本因此自建定时循环，同时检查 URL、table.inert 和首条记录。现有 wait 没有可直接表达这些组合条件的入口。

## Goals

- 等待明确的页面条件或页面 JS 谓词满足要求，支持运行时参数。
- 将页面等待的超时、检查间隔和失败信息统一交给工具处理。
- 优先复用 Playwright 等待能力，减少页面脚本中的 delay/waitFor。

## Non-goals

- 不在等待中提交业务操作，不提供读取接口并更新数据的步骤轮询。
- 不增加业务专属就绪检查，不保证页面数据在条件满足后永远不变。

## User scenarios

- 点击下一页后，等待目标页码、可交互表格和目标首行同时出现。
- 等待按钮可用、加载标记消失，或一个带参数的页面谓词返回 true。

## Acceptance

- 页面条件组合和 JS 谓词可以设置明确超时，并接收 T01 提供的结构化参数。
- 条件已经满足时立即完成；未满足时有界检查，超时按步骤失败处理。
- 失败信息包含等待条件和步骤位置，并复用现有失败证据收集。
- 页面条件、固定延迟等用途有明确的新配置和互斥规则，校验不通过旧参数优先级实现隐式适配。
- 单页导航及 SPA 路由变化下都有明确行为，避免仅凭 URL 改变宣告数据就绪。
- 顶层、分支及循环内的页面等待行为一致。

## Open questions

暂无必须由用户决定的未决事项。页面条件入口、固定延迟配置和谓词检查间隔在 Plan 中确定，以统一契约为目标。

## Decisions

- 页面谓词优先复用 Playwright 的 wait_for_function 等现有机制。
- 页面等待与 T05 的步骤轮询分开：前者观察页面，后者执行查询步骤并更新运行时数据。
- 不维护新旧等待参数的双路径；仓库内受影响的等待示例随本任务迁移。

## Risks

重载可能销毁页面执行上下文；谓词错误和正常的不满足条件需要区分，不能统一吞掉后等待至超时。
