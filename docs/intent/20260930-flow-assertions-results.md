## Background

evaluate 的结果主要显示在步骤消息中，执行器的最终返回未保留通用步骤结果。业务 flow 返回 failed 数量也不会自动导致失败；使用者无法仅凭 flow 成功判断业务是否符合预期。

## Goals

- 提供可声明的断言，明确表达业务期望并在不满足时失败。
- 输出可核对的命名结果及逐条处理结果，区分流程错误与业务分类。
- 使顶层、分支、循环及轮询中的结果与失败位置可追踪，支持自动化消费。

## Non-goals

- 不增加可视化报表平台、历史结果数据库或跨运行统计。
- 不把 ready/failed/skipped 设为所有流程的强制业务状态，也不默认要求所有记录成功。
- 不实现复杂聚合表达式语言。

## User scenarios

- 断言采集数量、唯一记录数和列表总数一致。
- 将逐条处理的分类结果收集为数组，输出总数及失败原因；是否允许失败由 flow 显式断言。
- CI 读取 JSON 结果及退出码，识别具体哪条记录和哪个嵌套步骤失败。

## Acceptance

- 断言复用 T02 条件，失败时包含用户可读的说明、引用值及步骤位置。
- 可显式导出命名结果，能收集集合迭代中的逐条输出供后续汇总；不只把结果拼进日志字符串。
- 顶层和嵌套的步骤与迭代结果具备一致的定位信息，轮询结果可区分完成、超时和读取失败。
- 未触发失败断言时，业务分类中含 failed 不自动改变 flow 成功状态；触发断言失败则明确返回失败。
- 结构化 CLI 输出可直接解析，运行日志与 JSON 结果分离；失败即使使用 --json 也返回非零退出码。
- 成功状态、截图和失败证据使用统一的新输出结构；不提供旧字段副本、旧 JSON 格式或旧退出码行为的适配。
- 长循环的详细结果有明确的输出控制与体积边界，不能无条件保存所有轮询响应。

## Open questions

暂无必须由用户决定的未决事项。断言字段、导出方式、迭代结果收集方式和详细输出开关在 Plan 中确定。现有 --json 混合日志及失败退出码行为的修正需显式说明。

## Decisions

- 通用报告只描述执行事实，业务汇总字段及成功政策由 flow 定义。
- T01 的结果绑定供后续执行消费，本任务负责断言、迭代输出收集及最终交付，两者使用同一数据契约。
- 用户已明确不做兼容适配；仓库内消费者和测试使用新协议，外部消费者按明确的变更说明迁移。

## Risks

报告涉及顶层与嵌套路径及 CLI 输出，现有自动化消费者需要迁移到新格式。结果收集也可能放大长循环的内存使用，应只保留明确需要的数据。
